# 表与笔记改版规划

日期：2026-10-29。状态：规划阶段；用户已确认下列产品规则，尚未修改业务代码、运行格式或真实数据。本文将已确认要求、实施建议与待定问题分开；未收敛前不得把建议当作正式接口契约。架构方向见 [ADR 0020](adr/0020-notebook-tables-and-content-permissions.md)。

## 1. 目标与现状

以可写正文、混合收纳内容的笔记式表替代现有事项。首页、日历和 AI 围绕表中内容工作；用户可以把作业、考试等主题单独组织起来。

当前运行版本仍采用 `matter | todo | event | knowledge` 四类成果，`event` 实际承担日历安排。新规划的“事件”另有含义，不能直接把两者视为同一概念，也不能仅把现有事项页面改名就算完成。

用户提供的手机笔记截图仅作列表排版参考：大标题、数量、分组、标题/摘要/日期有层次的卡片。截图内的笔记正文不构成额外功能要求。颜色、分组标准和表内具体布局还需状态稿细化。

## 2. 已确认：表与表内内容

- 表打开后采用笔记页形式，可以直接写正文，并添加待办、日程、事件等内容；不要求默认使用行列表格。
- 表可以混合收纳不同类型的内容。作业表可放作业要求、待办、安排和过程事件；考试表可放时间地点、复习待办、通知和普通笔记。
- 初始提供待办表、日程表、事件表。这三个默认表仅作为没有其他归属时的收纳位置，不是自动汇总全部同类型内容的主表；默认表禁止删除。
- 用户可以创建和删除自定义表。删除自定义表时连同其中内容一起进入回收站，保留 30 天；期间支持整表及其内容一起恢复，到期自动清理。
- 第一版支持自定义字段。表名和字段定义属于表结构；表正文与字段值属于内容。
- 普通知识作为笔记内容进入表。全局知识继续独立管理，AI 新增、修改、删除仍需人工确认，不因表内免确认规则而取消例外。
- 没有指定表且无其他明确归属的普通笔记放入事件表，类型仍为普通笔记，不因表名而变为事件。
- 自定义字段按表定义，每条内容分别填写值；首版支持文本、数字、日期时间、单选、多选、勾选六种类型。

“课程、章节、提交方式”是自定义字段的示例，不代表已经确认这三个内置字段。字段是否允许必填和默认值、各类型的输入边界、删改字段对已有值的处理仍待细化。

## 3. 已确认：待办、日程与事件

| 概念 | 已确认语义 |
|---|---|
| 普通笔记 | 文本和知识内容；无指定表且无其他明确归属时收纳到事件表，仍保持普通笔记类型；仅添加时间标签不使其进入日历 |
| 待办 | 以完成为目标、可勾选的行动，例如“周五前交作业”；允许没有日期，带截止时间仍保持待办类型，首页继续展示无日期的未完成待办 |
| 日程 | 未来要做且带有时间的安排，例如“周五下午考试” |
| 事件 | 对一件事的记录；在事件/日程的判别中，缺少“未来要做”或“带有时间”任一条件时记为事件 |

日程与事件有关联：事件可能导致已有日程变化。用户确认，收到“老师把考试从周五改到周一”时，保留一条调整通知事件，并更新原考试日程；不通过另建一场重复考试代替更新。两项均为表内内容操作，默认无需逐次确认。回复应说明实际记录与修改结果，不能把通知已保存说成日程已更新。

具体关联字段、一次联动的提交/恢复方式、日期或目标有歧义时的定位、通知重复送入时的去重仍需细化；目标不唯一时澄清对象属于查明事实，不是新增权限确认。

用户进一步确认：以完成为目标的待办与某时参加/执行的日程区分，“周五前交作业”是带截止时间的待办，“周五下午参加考试”是日程。事件/日程判别不覆盖明确的待办语义，不得因为待办有日期就自动复制成另一条日程。日历可以显示带时间的待办，但不会改变其类型；也不得因为时间过去就自行批量把日程改成事件。

## 4. 已确认：日历只负责显示

- 日历不拥有第二份内容；显示来自各表的待办、日程、事件等正式内容类型。
- 默认叠加全部表中符合日历显示条件且带时间的内容，并去重。
- 可以隐藏某张表、只显示一张表，或选择几张表叠加显示。
- 普通文章即使带时间标签，只要没有创建为待办、日程或事件，就不进入日历。
- 在日历发起编辑时，改动应回到来源表的同一份内容；不保存独立日历副本。

待细化：带时间的历史事件如何呈现、日期和时间段的具体含义、已完成待办的显示、重复安排和跨日内容的投影。建议用稳定内容身份和重复实例身份去重，不按标题相同自动合并；创建/编辑时间不充当日历业务时间。这些是实施建议，尚无新 schema。

## 5. 已确认：首页

- 保留现有今日安排、要做的、最近知识等内容区块；普通知识进入表后，最近知识区块的数据来源需相应投影，不能顺带移除它。
- 要做的继续聚合各表的待办，包含无日期的未完成待办。
- 在现有区块下方添加表展示模块，用户选择展示哪些表、调整已经添加的表的顺序。
- 每个表默认显示五行，可以展开。

建议“添加到首页”复用现有表，另设明确的新建表动作；从首页移除展示模块仅改变布局。首页是否继承日历表筛选、表内五行的排序与展开上限、布局是否跨端同步仍待确认。

## 6. 已确认：AI 内容与结构权限

| 操作对象 | 示例 | 默认确认规则 |
|---|---|---|
| 表内内容 | 读取、新增、修改、删除条目，修改表正文、时间、完成状态、自定义字段值 | 无需逐次人工确认 |
| 内容归属 | 在现有表之间移动内容 | 无需逐次人工确认 |
| 表结构 | 新建、删除、改名，新增/删除/修改自定义字段定义 | 在对话内确认后执行 |
| 全局知识 | 新增、修改、删除基础事实 | 继续独立管理与人工确认 |

三个默认表禁止删除，该规则不能通过 AI 工具绕过。表结构确认使用对话消息中的确认卡，移除独立待处理页。表内改动仍需由本地核心真实执行和反馈，免逐次确认不赋予模型任意文件或凭据操作能力。

建议确认卡展示实际表名、变更内容和删表影响范围；状态绑定具体候选和所见版本，重复点击不重复执行，内容变化后不复用旧确认。自定义表连内容删除的回收站保留期已确认为 30 天；普通单条内容删除和其他操作的撤销期限、批量行为仍待设计。

现有待处理页还承担草稿、捕获确认、同步冲突和全局候选。移除页面不意味着删除这些内容或自动裁决冲突：新的草稿入口、非对话捕获的确认入口、同步冲突入口与全局候选入口需要在实施前全部安排。

## 7. AI 定位、归类与查询

已确认：AI 数据查找围绕表内内容展开，新增/修改/删除的目标为表中内容；三个默认表不承担跨表自动汇总。无其他归属的待办、日程、事件分别进入对应默认表，普通笔记进入事件表但保持普通笔记类型。

建议流程：

1. 明确指定表时使用指定表；有明确主题归属规则时按规则定位现有表，目标不唯一时询问。
2. 无其他归属时使用已确认的默认归类规则；普通笔记进入事件表，不额外创建第四个默认笔记表，也不把普通笔记转换为事件。
3. 表不存在时，在对话提出新建表确认；未确认前不暗中创建，也不声称内容已归入该表。
4. 检索使用表、类型、时间和相关字段过滤，返回少量必要片段、来源表、内容身份和版本；按需读取正文，不因分表自动把整张表塞入上下文。
5. 修改日程前定位原内容；“更新原日程”和“新增另一场考试”需要区分，不根据相同标题静默合并。

按表过滤本身不保证检索性能。索引、预算和查询契约需要另行设计；既有按需检索、读取权限和版本检查不能在无新决定时自动取消。其他会话是否仍可被 AI 定向检索，也须在读取范围收敛时明确。

## 8. 已确认迁移与未定存储契约

已确认：旧事项迁移为表，保留正文及关联待办、事件。普通知识进入表；全局知识继续独立管理与确认。新功能不得以清空旧资料代替迁移。

当前仍遵守现行 Markdown 权威、SQLite 索引、本地会话隔离、稳定身份、墓碑和冲突保留规则。SQLite table schema 已升至 v10，表/内容格式已有首轮实现；P4迁移只在隔离目录/合成 fixture 演练，未移动或改写真实资料。

实施中已收敛的决定与剩余边界：

- 表正文、表结构、内容归属与字段值的首版权威格式已落入数据契约及模型；跨端同步格式仍未切换。
- 旧事项/待办/知识的迁移映射已有首轮预检。未来且有开始时间的旧日历项可迁为日程；过去或无开始时间的记录不能证明实际发生，预检要求人工判定，不自动写成事件。
- 无事项归属的待办、未来旧日历安排、普通知识分别进入默认待办表、日程表、事件表；知识单一事项关联归入该表，其他关联保留原 link。
- 默认表身份、不可删除约束和本地索引重建已实现首轮；跨端导入行为仍待同步 ADR。
- 单条/整表恢复事务及到期清理已有本地首轮实现；跨设备恢复与同步墓碑交互仍待同步 ADR。
- Vault Markdown 备份清单、迁移暂存、幂等重放和 hash 回滚已通过合成 fixture；SQLite/会话/settings 与 vault 的一致性总清单、容量探测、启动迁移门和只读旧格式入口尚未实现。真实资料未迁移。

建议一条内容只保存一份，归属变化保持身份稳定；继续避免按表标题移动底层文件和整表大文件造成冲突放大。这不构成已经确定的新目录或字段设计。

## 9. 后续细化与验收场景

逐步实施顺序、文件落点、依赖、局部验证和完成标准见[执行计划](table-notebook-implementation-plan.md)：P0–P7已有首轮实现，P5表页响应式验收及P8–P9待执行；其中建议默认值不自动成为用户已确认决定。

已收敛普通笔记兜底位置、待办与日程边界、自定义字段作用范围和首版六种类型，以及保留通知事件并更新原日程、删表连内容保留 30 天且支持整表恢复。执行建议、页面文字稿和 AI 工具草案见[交互契约](table-interaction-contract.md)；未被用户明确指定的实现细节仍需按证据调整。

以下为未来实现的验收场景，全部尚未执行：

1. 空表可以只写正文；同一表加入待办、日程、事件和普通笔记。
2. 作业表中的待办不自动复制进默认待办表，但可出现在首页和日历投影。
3. 日历默认叠加各表，单表/多表筛选可用，同一内容不因多个投影重复展示。
4. 普通笔记有时间标签仍不进入日历；正式带时间内容按最终确定规则展示。
5. 首页保留无日期待办；添加表展示、排序、五行摘要和展开可用。
6. AI 修改正文、条目、字段值和跨表移动不逐次确认；结构变更在原对话确认且只执行一次。
7. 默认表不能通过界面、AI 或恢复/同步旁路删除；自定义表及其内容一起进入回收站，删除后 30 天内可整表恢复，到期自动清理。
8. 事件导致原日程变更时，保留通知事件并更新原日程，不漏改、不重复创建；目标有歧义时询问，两项实际操作结果可核对。
9. 全局知识仍须确认，不能通过移入普通表或修改用途标记绕过。
10. 旧事项迁移后正文与关联内容保留；旧日历安排和普通知识不丢失、不误分类。
11. 移除待处理页后，草稿、捕获确认、全局候选和同步冲突仍有完整处理入口。
12. 未指定表的普通笔记进入事件表，仍是普通笔记且不因时间标签出现在日历；带截止时间的待办不被改成或复制成日程。
13. 字段定义在表内共享，各条内容分别填写值；首版六种类型可使用，字段值改动与字段定义变更遵循各自的权限边界。
