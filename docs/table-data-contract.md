# 表与内容数据契约草案

状态：本地数据契约已首轮实现（SQLite v10、独立 Markdown 表/条目、搜索、恢复、投影、迁移门）。Android候选已在空 AVD 以合成旧格式文件完成应用内迁移、重启读回和源哈希核验；真实资料未处理。跨端表同步格式仍沿用旧协议且未实现。若发现数据丢失或同步不变量冲突，先更新此契约与 ADR 0021。

## 存储对象与身份

- 一个表一个 `tables/<table-id>.md` 文件；一条内容一个 `items/<item-id>.md` 文件。内容 ID 不含标题和表名，移动表不改变路径或 ID。
- Markdown 是表和内容的权威正文；SQLite 表/内容行、日历投影、全文片段均可重建。同步对象 ID、文件名 ID、frontmatter ID 必须相同。
- 表字段：`id`、`type: table`、`schema_version`、`role: inbox_todo | inbox_schedule | inbox_event | custom`、`title`、`revision`、`created_at`、`updated_at`、`deleted`、`field_definitions`。正文是表的自由文本。
- 内容字段：`id`、`type: note | todo | schedule | event`、`schema_version`、`table_id`、`title`、`revision`、`created_at`、`updated_at`、`deleted`、`tags`、`links`、`custom_values`。全局知识不进入该契约，继续使用现有独立存储与审批。
- `note` 正文是普通笔记；时间文字及创建/修改时间不是业务时间。`todo` 可有 `due`、`done`；`schedule` 有 `start`、可选 `end`、`all_day`、基础 `recurrence`；`event` 有可选 `occurred_at`；日期全部用 ISO 8601，时间类值必须带时区。
- 调整通知事件使用 `affects: [<schedule-id>]` 关联被修改日程，并可保存变化来源/说明。通知事件保留原有事实，更新同一日程对象的版本；不创建第二个考试内容。

## 字段定义与字段值

每个表的 `field_definitions` 项有稳定 `id`、`name`、`type`、`options` 和可选 `required`/`default`。类型只允许 `text | number | date | single_select | multi_select | checkbox`。字段项可以被任意内容类型填写；空值与布尔 `false` 区别表示。

`custom_values` 以字段 ID 为键，值按定义校验。字段改名保留 ID 和值；删除字段将受影响条目展示给人确认，字段定义和受影响条目的原值作为同一批本地可恢复变更保留 30 天。恢复中的字段变更会阻止该表其他恢复/联动批次，避免前像交叉覆盖；改类型先验证全部已有值，不能完整转换时拒绝整体变更并列出不兼容 ID。表内值修改是内容操作；字段定义增删改是表结构操作。

## 所属表和默认表

默认表是应用种子表，使用稳定角色和应用保留 ID，不由标题判断：无归属待办→待办默认表，无归属日程→日程默认表，无归属事件与普通笔记→事件默认表。普通笔记仍为 `note`。全局知识不移入默认事件表，继续使用现行独立审批语义。

每条内容至多有一个主要 `table_id`。显式移动更新 `table_id`，不变更身份；`links` 保留额外关联。跨表字段定义不匹配时不得新建目标字段或清空值：移动前显示差异，用户解决映射后才提交。目标表及源表都要在一次可恢复提交中校验。

## 日历投影

- `todo` 的 `due`、`schedule` 的 `start/end`、具有 `occurred_at` 的 `event` 可以形成投影；`note` 绝不投影。没有业务时间的事件/待办留在表和首页。
- 日历保存设备级过滤设置和视图状态，不复制/另存内容；每个投影含源内容 ID、源表 ID 和重复实例 ID。按该身份去重，点击编辑源对象。
- 表显隐独立于首页选择；首页现有未完成待办跨所有表聚合，包括无截止时间；首页最近知识包含普通笔记但排除独立全局知识。

## 删除、恢复和同步

- 整表回收站项包含批次 ID、表前像、该表内容的 ID/版本/文件前像清单、删除和到期时间；保留 30 天。到期删除前像，正文仍按同步协议形成删除标记。
- 删除的表若有跨表事件通过 `affects` 指向其日程，删除批次同时保存并移除这些外部反向关联；整表恢复时复原。不得留下指向已删除表日程的悬空链接。
- 单条待办/日程/事件/笔记的 AI 删除走既有 10 分钟撤销窗口；整表及其中全部当前内容另走用户确认的 30 天回收站。内容范围的期限不继承整表期限。
- 删除批次提交需具备幂等键；恢复整批保留 ID/关联并以版本/hash 比较。删除后内容在别处有更高版本时不得静默覆盖，保留冲突并停止冲突对象恢复；其余对象逐条报告状态。
- 本端 30 天可恢复是用户已确认的要求；恢复前像是否同步到其他端、云盘备份和墓碑保留交互属于新的同步 ADR 决策，不宣称已实现。
- 表在同批内容之前导入；表缺失、版本未知、身份/路径/hash 错配的内容不得静默归到默认表。冲突副本和删除标记遵守既有协议，表结构并发冲突不做字段并集合并。

## 旧资料迁移建议

- `matter`→表，沿用 ID；相关 `todo`→同一表内的待办。旧日历 `event` 只有在开始时间明确晚于迁移时刻时自动转为日程。开始时间已到/已过或缺失时，旧数据不能证明事情是否发生，预检阻断自动迁移并要求人工判定，避免虚构事实。
- 无 matter 的 `todo`→默认待办表；无 matter 的旧日历安排→默认日程表；普通知识→事件默认表中的 `note`。全局知识维持原类型、范围和确认状态。
- 旧知识只链接一个 matter 时，可建议迁入对应表；链接零个或多个 matter 时放事件默认表并保留全部链接。自动迁移不按标题猜关系、不复制内容。
- 先快照备份，再输出预检计划和数量/hash 清单；暂存器生成新格式，通过 ID/正文/关系核验后幂等复制到新路径并写完成标记。旧源文件保留，应用入口切换必须等待独立迁移门完成，不能把“新文件复制完成”当作原子切换。失败时可依 journal 重放或按 hash 条件回滚新文件，旧库和 vault 源件继续保留。
- `TableMigrationService` 已备份 vault Markdown，并要求 SQLite/会话库/设置快照回调，完成后将两类清单路径写入迁移 journal。`SqliteMigrationCoordinator` 的独立快照可幂等校验；Android/Windows可用空间探测、启动只读门和用户确认的副本生成流程已接入。候选 APK 已在空 AVD 安装并对合成旧格式目录走过 UI 确认迁移和重启；真实资料仍未迁移。应用运行门只暂停本进程可写模块，跨进程/系统同步写入无法同时冻结，不能声称真实跨存储一致迁移；旧格式同步协议尚未切换。

## 版本与兼容

表与内容版本分别递增，未知主版本只读并明确报告，禁止降级覆盖。旧库首次迁移前不可删除旧格式读取能力；应用回滚时使用迁移前快照恢复完整旧库/vault。同步协议现行四类成果白名单在数据格式决策完成前保持现状，不提前推送新表格式。
