每例为一个完整任务：准备隔离资料 → 通过 UI 操作 → 模型/平台响应 → 查看反馈 → 验证存储和副作用。通常 6–12 步，至少两项断言，至少一项为真实状态、持久化或调用计数；不能只断言“无异常”或“有文字”。复杂流程可多于 12 步，不为凑步数增加无意义导航。

用例编写时补齐明确种子、脚本、步骤、主题/字体、预期对象 ID/版本/工具次数和清理条件；表中的关键断言是必须实现的最低标准。每个 ID 固定一种平台配置；同一例中的多个输入检查仍是一项任务，不将数据变体和失败重试另计为新增例。

检索的零调用、限额和停止以端内计数及实际请求体判断，不看 AI 自称“没有检索”。审批以有效成果与候选账本判断，不只看确认卡。写入以 Markdown/SQLite/版本/hash 判断，不只看回复“已完成”。

## 3. 覆盖、证据与替身边界

所有用例同时断言异常/溢出未发生；按任务表分配浅深色、大字体、窄屏/宽屏和键盘配置，不另外堆成全项目测试。SEC-011–022 覆盖 8 种权限组合及默认、独立保存、在途撤权。SEC-023–040 是省检索的专门门禁，必须能观察执行层计数。

SEC-005/013/022/052/054/057/061/063/070 以及 SEC-077–082 使用真实临时存储验证对应迁移/版本/重放状态；其他例也不能用一个文本假回复代替成果/审批断言。恢复类记录是否为 Flutter 生命周期重建、数据库重新打开或 OS 强停探针；三者不是同一种证据。

模型、语音识别返回和远端同步可使用确定性替身，保证复杂失败可复现；报告每例替身模式。SEC-077/082 的多个端库是受控同步状态，并不表示同时启动三台设备或完成真实 OneDrive 联调。无法操控的第三方系统文件选择器、真实麦克风采集和真实 TTS 出声需补平台探针，未执行的部分写明“未执行”，不把替身成功扩大成真实能力通过。

阶段 S11 已将每个 ID 的平台、任务和状态断言写入机器数据；完整性检查覆盖 100 个连续唯一 ID、平台及类别数量、有效断言。宿主完整 100/100、设备试跑 10/10 已通过。S12 仍需以干净提交 SHA 执行手机 50、平板 25、Windows 25；宿主通过和设备试跑不能替代完整设备验收。
