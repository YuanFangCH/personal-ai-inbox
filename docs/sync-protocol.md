# 成果同步协议

> 版本：1.2
> 日期：2026-10-05
> 1.1 变更：`type` 定为 `matter | todo | event | knowledge`（移除 `note`），新增 `matter`、`links`、`recurrence` 字段，补充归属、关联与重复规则。
> 1.2 变更：明确 AI 会话、消息、工具调用审计和本地图片附件永不进入同步区。
> 适用：个人 AI 收件箱与提醒系统 v2.2
> 相关：[可执行方案](personal-ai-inbox-executable-plan.md)、[术语表](../CONTEXT.md)、[ADR 索引](adr/README.md)

## 1. 目标与边界

三端各自独立工作，只在云盘上交换定稿成果。没有集中式后端，没有实时同步，没有局域网直连。

协议只解决四件事：谁变了、谁新、冲突怎么办、删除怎么传。它不解决捕获、OCR、模型调用和提醒，那些在端内完成。

不做的事：不做实时推送、不做字段级合并、不做原始素材同步、不做端到端加密（当前版本）、不做服务端仲裁。

## 2. 传送通道

| 通道 | 角色 | 方向 | 频率 |
|---|---|---|---|
| OneDrive（App Folder） | 双向同步主通道 | 读 + 写 | 每 15 分钟 + 事件触发 |
| 百度网盘 | 单向发布 / 留档 | 只写不读 | 每日一次 |
| 个人服务器 | 预留 | — | 未实现 |

通道通过 `SyncProvider` 接口抽象，最小动词集：列变更、上传、下载、删除、标记冲突。新增通道不得改变本协议的数据模型。

## 3. 成果文件与 frontmatter

一个成果一个 `.md` 文件，权威副本在本地 vault，同步区是它的镜像。类型只有四种：`matter`、`todo`、`event`、`knowledge`。

```yaml
---
id: mt_20261004_7f3a91
type: matter          # matter | todo | event | knowledge
title: 英语比赛
status: canonical     # draft | reviewed | canonical
origin_device: honor-phone
revision: 3
created_at: 2026-10-04T09:12:00+08:00
updated_at: 2026-10-04T09:40:00+08:00
deleted: false
tags: [比赛, 英语]
links: [kn_20261004_abc]
---

正文……
```

按类型的落点与附加字段：

| type | 目录 | 附加字段 |
|---|---|---|
| `matter` | `matters/` | 无；正文放要求、背景、过程记录 |
| `todo` | `todos/` | `due`（可空）、`done`、`matter`（可空） |
| `event` | `calendar/` | `start`、`end`（可空）、`all_day`、`recurrence`（可空）、`matter`（可空） |
| `knowledge` | `knowledge/` | `source_event_ids`、`source_hashes` |

字段约定：

- `id` 稳定且唯一，生成后永不改变；文件名就是它。
- `revision` 是本端递增整数，跨端不做唯一性保证。
- `updated_at` 用带时区的 ISO 8601，时区为 `Asia/Hong_Kong`。
- `deleted: true` 时为墓碑，正文清空，仅保留 frontmatter。
- 文件里不写 `content_hash`，避免自引用；hash 由同步层计算并存在本地索引里。
- `recurrence` 只支持基础重复：每天 / 每周 / 每月加一个结束条件，写成 RRULE 字符串；不做例外日期、农历和 ICS 订阅。

**归属与关联**

- 归属：待办与事件用 `matter: <id>` 声明所属事项；事项文件不列子项。`matter` 可以为空，允许“买牛奶”这类独立行动。
- 关联：平级关系（事项 ↔ 知识、知识 ↔ 知识）用 `links: [<id>]`，只在创建关系的一侧写一次。
- 反向引用（事项下面有哪些待办、哪条知识被哪些事项引用）由本地索引派生，不写文件、不参与同步。
- 关联改动按整文件冲突处理，不做并集合并；并集分不清新增与删除，会把已删除的关联救回来。
- 不自动建立关联：没有 embedding、没有向量索引、没有相似度推荐。
- 待办不嵌套：`todo` 不指向 `todo`；需要多个行动时建一个 `matter` 来装。

## 4. 目录与命名

```text
SyncZone/
├── matters/<id>.md
├── todos/<id>.md
├── calendar/<id>.md
└── knowledge/<id>.md
```

- 文件名只用 `id`，绝不用标题；改标题不会造成云盘上的删除 + 新增。
- 本地 vault 与同步区相对路径一一对应。
- 文件永远按类型平铺，不按事项分组：换归属不能导致文件移动，否则云盘会误判成一删一增。
- `vault/drafts/`、`vault/raw/`、`vault/inbox/` 显式排除，永不同步。
- `draft` 状态的成果不出现在同步区；转为 `canonical` 时才写入。
- AI 会话数据库、消息、工具调用审计与本地图片附件独立于 vault 和同步区，永不参与同步。

## 5. 变更判定

每个成果在本地索引里存三个值：

- `local_hash`：本地当前文件字节的 SHA-256。
- `last_synced_hash`：上次同步成功时的文件字节 SHA-256。
- `remote_etag`：上次同步成功时对端返回的 `eTag`。

判定规则：

| 远端 hash vs 上次同步 | 本地 hash vs 上次同步 | 结论 |
|---|---|---|
| 相同 | 相同 | 无变化，跳过 |
| 相同 | 不同 | 只有本地改了，上传 |
| 不同 | 相同 | 只有远端改了，下载覆盖 |
| 不同 | 不同 | 真冲突，见第 6 节 |

`updated_at` 只在真冲突裁决时使用；仍相同则按 `origin_device` 字典序破平局。

这个设计不依赖任何一台设备的时钟准确，也不引入向量时钟（见 [ADR 0005](adr/0005-three-hash-change-detection.md)）。

## 6. 冲突处理

真冲突时：

1. 本地版本保持原位，`revision + 1`。
2. 远端版本原样落成 `<id>.conflict-<device>-<yyyyMMddHHmm>.md`，放在同目录。
3. 冲突副本进入确认队列，App 行内显示冲突徽标。
4. 用户裁决后，把选中的内容写回 `<id>.md`，删除冲突副本。

绝不静默覆盖。冲突副本本身不参与后续自动合并。

## 7. 删除与墓碑

- 删除成果时，把 `<id>.md` 改写成 `deleted: true` 的墓碑，正文清空。
- 墓碑同样参与同步，其他端据此删除本地对应成果，而不是因为“文件消失了”去猜测。
- 墓碑保留 30 天，由任一端在同步轮次中清理过期墓碑。
- 删除与修改同时发生算真冲突，走第 6 节，不自动删除。

## 8. 同步轮次

OneDrive 双向同步每轮执行：

```text
1. 读取上次保存的 deltaLink（首次为空）
2. 调用 /delta 拉取变更项（含新增、修改、删除）
3. 对每个变更项按第 5 节判定：
   - 接受远端写入
   - 或标记本地待上传
   - 或制造冲突副本
4. 处理待上传队列：PUT content，带 If-Match: <remote_etag>
   - 返回 412 Precondition Failed 说明远端又变了，回到第 3 步重判
   - 成功则更新 local_hash / last_synced_hash / remote_etag
5. 保存新的 deltaLink
6. 更新每条成果的同步状态
```

补充规则：

- `410 Gone`：deltaLink 失效，退回一次全量枚举，不丢变更。
- 每轮处理对象数设上限（默认 200），超出的留到下一轮，避免长时间占用。
- 首次接入时本地可能已有成果，按同一套规则合并，真冲突进队列。

## 9. 触发与调度

- 周期：每 15 分钟一轮（目标值，不是硬承诺）。
- 事件触发：成果定稿、App 回到前台、手动下拉。
- 网络：WiFi 优先；蜂窝允许，但单次传输上限 5 MB。
- 充电且空闲时做一次全量校验，用于发现漏网差异。
- Android 用 WorkManager（最小间隔 15 分钟，受 Doze 与厂商省电推迟，接受 best-effort）。
- Windows 用任务计划程序，登录与唤醒后补跑。

## 10. 失败与重试

- 退避序列：1 / 5 / 15 / 60 分钟，上限 6 次或 24 小时。
- 单条成果失败不阻塞其他成果。
- 超过上限后停止自动重试，进入同步总览页等待手动重试。
- OAuth 令牌失效：暂停同步并提示重新登录，本地功能不受影响。
- 所有失败都记录 `object_id`、阶段、错误码与时间，便于定位。

## 11. 首次接入

1. 安装 App，用同一个 Microsoft 账号登录。
2. App 通过 `special/approot` 定位同一个 App Folder，无需配对码。
3. 首次生成稳定 `device_id` 并存入本地安全存储。
4. 执行一次全量同步，按第 5 节规则合并已有成果。
5. 有真冲突则进入确认队列，不做静默覆盖。

## 12. 百度网盘归档

- 每日一次，默认在本地时间 03:00 后首次联网时执行。
- 收集全部 `status: canonical` 的成果 `.md`，打包成 `ai-inbox-YYYY-MM-DD.zip`。
- 上传到 `/apps/<应用名>/archive/YYYY/MM/`。
- 只写不读，不参与冲突检测，不作为恢复的唯一来源，不删除历史归档。
- 归档内容只有成果与墓碑 frontmatter，不含原始素材。

## 13. 状态呈现

每条成果带一个同步状态：已同步 / 待上传 / 待下载 / 冲突 / 已删除。

同步总览页展示：最后同步时间、各通道状态、失败与重试队列、冲突队列。

## 14. 安全与凭据

- 每端独立 OAuth，令牌存系统安全存储（Android Keystore、Windows Credential Manager + DPAPI）。
- 应用注册为 public client + PKCE，App 内不放 client secret。
- 云模型 API Key 同样按端存放。
- 令牌与密钥不写入代码、配置文件、文件名或 URL。
- 成果在云盘里默认可读；端到端加密是独立的后续版本，不在本协议内。

## 15. 不变量

任何实现都必须满足：

1. 同步区只有 `canonical` 成果、墓碑和冲突副本，没有草稿与原始素材。
2. 一个成果一个 `.md`，文件名是稳定 `id`。
3. 冲突永不静默覆盖。
4. 删除永远留墓碑，不靠文件消失传播。
5. 删掉 SQLite 索引后，能从 `.md` 文件重建全部成果。
6. 单条成果失败不阻塞整轮同步。
7. 任何通道异常都不影响本地捕获、编辑、查看与提醒。
8. 归属只由子项的 `matter` 字段声明，事项文件不列子项。
9. 关联单边存储，反向引用只从索引派生。
10. 不自动建立关联，不维护向量索引。
11. 待办不嵌套待办，多行动只由事项聚合。
12. AI 会话与消息永不进入同步区；自动记录生成的成果按本协议作为普通成果同步。
